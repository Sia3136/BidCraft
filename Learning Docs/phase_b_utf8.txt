<p><strong>Phase b learning doc</strong> <br />This explanation breaks down the architectural choices, alternatives, industry standards, and failure points for each of the five features implemented in Phase B. </p><p>---</p><p>## 1. Live Auction Engine (WebSockets)</p><p>### Why was this pattern chosen?</p><p>We chose a **stateful WebSocket server with rooms** (Socket.IO) attached directly to the Express server. </p><p>* **Real-time updates**: Sockets support full-duplex communication. The browser doesn't have to keep asking "are there new bids?" (polling); the server pushes bids down to the clients instantly.</p><p>* **Rooms separation**: By placing users into room `auction_${auctionId}`, we prevent broadcast noise. A user viewing a watch listing won't receive traffic from a painting listing.</p><p>### Three Alternative Implementations</p><p>1. **Short Polling**: The frontend runs a `setInterval` fetching `GET /api/auctions/:id` every 3ΓÇô5 seconds. </p><p>2. **Server-Sent Events (SSE)**: A unidirectional HTTP channel where the server streams updates. Better than polling, simpler than WebSockets since it is pure HTTP, but doesn't handle bidirectional real-time traffic naturally.</p><p>3. **Dedicated Pub/Sub + WebSockets (e.g. Redis + Socket.IO Adapter)**: Decoupled architecture where backend APIs publish events to a Redis channel, and separate stateful WebSocket worker servers subscribe to Redis to push messages to users.</p><p>### Industry-Standard Approach</p><p>For production-grade real-time bidding, the standard is to run **decoupled serverless/microservice socket gateways** (like AWS API Gateway WebSockets, Pusher, or Ably) backed by an in-memory queue/cache (Redis Pub/Sub). This prevents the main API server from running out of memory due to thousands of persistent, open connections.</p><p>### Where could this code fail?</p><p>* **Horizontal Scaling (No Shared Adapter)**: Currently, state is stored in the memory of the single Node process. If you run multiple server instances behind a load balancer, a user connected to Server A won't see a bid broadcast by Server B. (Fix: add `@socket.io/redis-adapter`).</p><p>* **Connection Drop Handling**: If a user loses internet connection momentarily and reconnects, they might miss the `auction_won` or intermediate `bid_placed` events.</p><p>---</p><p>## 2. Shipping Integration (JSONB Storage)</p><p>### Why was this pattern chosen?</p><p>We added a `shipping_address` JSONB column to the `orders` table.</p><p>* **Schema flexibility**: Address structures differ vastly by country (e.g., postal codes vs. zip codes, states vs. prefectures). Storing addresses as JSONB avoids complex table normalization for nested address structures.</p><p>* **Immutable Snapshot**: An order address must remain frozen exactly as it was entered at checkout, even if the user later updates their profile address. Storing a JSON blob copies that data at a specific moment in time.</p><p>### Three Alternative Implementations</p><p>1. **Normalized Table**: Creating an `addresses` table (`id`, `user_id`, `street`, `city`, etc.) and referencing `address_id` in `orders`.</p><p>2. **Flat Columns**: Adding `shipping_fullname`, `shipping_address_line1`, etc., directly to the `orders` table.</p><p>3. **Separate Shipping Microservice**: Delegating all shipping, tracking, and label generation details to an external API (like Shippo or EasyPost) and storing only the third-party shipment reference token.</p><p>### Industry-Standard Approach</p><p>The standard is a hybrid: a **user-profiles address book** (normalized database table) for address selection, combined with a **JSON snapshot copy** saved directly on the Invoice/Order record to ensure immutability.</p><p>### Where could this code fail?</p><p>* **Bad Data Structure / Lack of DB Constraints**: Because JSONB allows arbitrary structures, a bug in the code could write `{ "zip": 12345 }` instead of `{ "postalCode": "12345" }`, bypassing database validations. (Fix: enforce database-level JSON schemas or Joi schema validation before query execution).</p><p>---</p><p>## 3. Buyer Dashboard (Tabbed Views)</p><p>### Why was this pattern chosen?</p><p>We chose a **Client-Side Tabbed Router Component** that queries a single, authenticated endpoint (`/api/orders?role=buyer`).</p><p>* **Performance**: It minimizes client bundle size by reusing base layout containers, and filters the returned items efficiently using queries.</p><p>* **Security boundary**: Relying on `/api/orders?role=buyer` coupled with server-side authorization ensures users cannot fetch orders belonging to other buyers.</p><p>### Three Alternative Implementations</p><p>1. **Server-Side Rendered (SSR) Subpages**: Separate folders for `/dashboard/buyer/orders` and `/dashboard/buyer/disputes` with Next.js page transitions.</p><p>2. **GraphQL Queries**: Querying exactly what is needed for the active view in a single round-trip.</p><p>3. **State Management Sync (e.g. Redux / Zustand)**: Hydrating all user data on app mount and slicing the store client-side.</p><p>### Industry-Standard Approach</p><p>For dynamic apps, standard practice is **Client-side data fetching with SWR or React Query** targeting separate REST endpoints, leveraging optimistic UI updates for interactions like "Confirm Delivery".</p><p>### Where could this code fail?</p><p>* **Session Expiry**: If the `accessToken` expires while the page is open, requests fail silently without redirecting the user back to the login screen.</p><p>---</p><p>## 4. Seller Dashboard (State-Driven UI)</p><p>### Why was this pattern chosen?</p><p>We chose a **State-Driven UI** that dynamically renders forms (like the tracking form) based on the order's primary status (`paid`).</p><p>* **UX clarity**: Sellers only see tracking input options when an action is required (preventing tracking inputs for already-shipped orders).</p><p>### Three Alternative Implementations</p><p>1. **Static Table Routing**: Showing a flat table where clicking "Ship" opens a full page checkout-like flow `/orders/[id]/ship`.</p><p>2. **Modals**: A slide-over modal for submitting tracking information rather than inline forms.</p><p>3. **Excel-like Inline Grid Edit**: Allowing batch edits directly inside a sheet of pending orders.</p><p>### Industry-Standard Approach</p><p>The industry standard is to use **Design Systems (e.g., Shadcn/UI, Tailwind)** with multi-step workflows. Long forms are broken down into wizard components, and state is preserved across steps.</p><p>### Where could this code fail?</p><p>* **Optimistic UI Errors**: If the API call to update tracking fails after clicking "Save", the UI must revert the state immediately; otherwise, it looks shipped when it wasn't.</p><p>---</p><p>## 5. Notifications (Polled/Real-Time Feed)</p><p>### Why was this pattern chosen?</p><p>We chose a **Dropdown navbar component** that loads initial database-backed notifications on mount.</p><p>* **Historical feed**: If a user goes offline, a pure WebSocket notification would be lost. By storing notifications in the database and loading them on mount, we ensure the user never misses messages.</p><p>### Three Alternative Implementations</p><p>1. **Push Notifications (Service Workers)**: Browser-level Web Push notifications that trigger even when the BidCraft website is closed.</p><p>2. **Pure WebSocket Broadcasts**: Ephemeral toast popups that are only seen if the app is active, with no historical inbox.</p><p>3. **Email-Only Alerts**: Zero UI footprint; alerts are offloaded entirely to Sendgrid/Mailgun.</p><p>### Industry-Standard Approach</p><p>Industry standard uses a **unified notification engine** (e.g. Courier or Novu) that writes to a persistent inbox database while simultaneously broadcasting to socket channels (for active sessions) and triggering email alerts.</p><p>### Where could this code fail?</p><p>* **N+1 DB Loading Issues**: If not optimized with proper indexes, fetching user notifications can slow down when a user's notification list grows into thousands of entries.</p>
